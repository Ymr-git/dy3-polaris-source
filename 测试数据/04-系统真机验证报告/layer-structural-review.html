dy3-polaris 7+2 分层编码的深层结构性问题评审

本报告聚焦"分层编码方式本身"带来的结构性问题（区别于前几轮已修复的接口错误/休眠/边界场景）；日期：2026-08-07

一、总论：纵向分层到位，横向治理缺失

7+2 把系统按"层"纵向切分（每层路由/模型/服务完整），但缺少四个横切面治理，导致分层架构最典型的四类病全部出现：

横切面应做现状后果
① 契约管理层间接口单点定义+版本化+自动校验错误码分散硬编码、响应信封三套并存、方法名三套、无 IDL联调故障、前后端适配成本
② 数据归属每类数据唯一写方（Single Writer）画像 8 条写路径、会话三套、策略四套、知识目录倒挂在 L7 展示层口径漂移、并发覆盖、双轨语义
③ 观测性trace_id 贯穿 + 真实探活 + 指标接入无请求级 trace、health 硬编码 healthy、4 套指标引擎零接线跨层故障不可追溯、监控盲区
④ 安全边界网关覆盖全部入口 + 层间信任传递仅 L1+WS+L5 agent-run 鉴权；L2/L3/L4/L6/L7 全开放任意写端点可被调用

二、职责归属模糊 → 双轨/三轨系统（最核心问题）

功能规范归属实际实现处重叠度具体冲突
会话生命周期L1 用户会话L1 + L2 + L5 三套（各带状态机/Fork/超时，session_id 互不认识）高一次问答隐式建 L5 会话，L1 列表查不到；三套 active↔paused↔closed
画像写入L2 唯一写方10 条路径：L2 练习/事件/播种 + L5 审核/导学/考核/反馈桥高L5 直改 kp_mastery/confidence；version 乐观锁 8 个写方无一使用
画像构建算法L2 profile_builder 管线管线（冷启动/漂移/生命周期）沉睡 vs practice.answer 手工补丁高两套计算口径（管线含衰减 vs 补丁只写 BKT 后验），运行时走补丁
学习策略L4 决策引擎四套：L4 process_query（兜底）/ L5 run_guidance（主）/ L5 path_simulation（推荐）/ L6 stub中高"决策"三语义（行动类型/答复置信度/KP 步骤）；L4 被降级为失败兜底
反馈闭环L1 HiTL / L4 决策反馈四处 + 4 套 feedback_type 枚举（l1/l4/l2/l0）中同一反馈事实无法跨通道聚合；L5 把"置信度"当"评分"写入画像
知识点目录L2（设计 §2.1.1）唯一完整定义在 L7 渲染常量；L2 硬编码 NODE_TO_KP（仅 10/42）；L3 用 KP-001/DOM-A-01 三套 ID 风格中架构倒挂：展示层持有领域目录；32 个 KP 无题可练

根因：分层只约束了"文件放哪层"，没有约束"谁可以写什么"。L5 作为编排层是最大越界方（写画像/建会话/产策略/发反馈），与"分层"初衷相悖。

三、数据一致性：跨层用例无事务、无补偿、无幂等

四、SSOT 缺失：领域事实多副本且互相冲突

事实副本数数值冲突
Dy3+ 发射波长4 处（l2 题库 / l3 seed / l0 kpa / l3 fact_check）黄光 571 vs 574 vs 575 vs 580；红光 659 vs 660 —— 生成与审核互相误报
42 KP 域定义≥4 份（L7 常量 / 前端 JS / L2 NODE_TO_KP / L3 锚点）ID 风格三套（A-01 / KP-001 / DOM-A-01），无外键校验
StandardValueStore默认空（仅容差表）事实校验实际无标准值可用

五、观测性：跨层链路不可追踪

项现状后果
链路追踪无请求级 trace_id 中间件；L0 内部 trace_id（522 处）靠函数传参与 L1-L7 隔离；L7 error_payload 的 trace_id 恒空/api/query → L5 → L2/L3 日志无法串联，排障靠猜
健康检查L2 /l2/health 硬编码 "healthy"；L5/L6 只判依赖对象是否为 None（"假探针"）监控/负载均衡收到假阳性信号
指标l3/metrics（Prometheus 风格）、governance MetricsEngine、AgentHealthTracker 等 4 套全部零接线；无 /metrics 端点QPS/时延/成功率不可观测
错误体系-32xxx 分散硬编码无注册表；-32000 在 governance 与 L6 语义不同；L7 改用字符串码错误码冲突掩盖真实类型

六、工程债：组装、测试、配置、依赖

项现状风险
组装create_full_app_builder 约 250 行"上帝工厂"；SkillExecutor 空依赖占位后 app._skill_executor.deps=... 私改注入；L2Router 内部隐藏 new 服务单层测试难、替换实现难、封装破坏
测试138 个测试文件 4.48MB，但跨层集成测试仅 2 个（1.4%）；tests/l3、l6、l7 目录缺失全散根目录；部分测试"测实现不测契约"跨层重构回归风险高，层间漂移测不出
配置4 处互不相通（L6Config 唯一结构化，但组装时完全不读）；L2-L5 阈值全部硬编码部署差异无法配置表达
依赖pyproject 13 个依赖全为 L6 基础设施，无锁文件；.venv 有 pandas/numpy 未声明不可复现、影响面不明

七、安全边界：分层≠安全隔离

层鉴权状态
L1 /l1/*✅ 全鉴权（仅 health/login 开放）
WS 三通道 + L5 agent-run✅ JWT + Agent 权限矩阵
/api/query、L2 全部、L3 全部、L4 全部、L5 其余、L6 全部、L7❌ 完全开放——任意 learner_id 可读写任意画像；/l3/persistence/restore 可未鉴权覆盖知识库；/l6/a2a/agents 可注册

层间进程内直调零信任校验：单体部署尚可容忍，拆分服务后即全面暴露。CORS allow_origins=* 亦无限制。

八、演进与部署：单进程单体的天花板

项现状
部署形态单进程单体，L0-L7 同进程共享内存；各层 Router 有 create_app() 可独立跑但无多进程配置
分布式支持L6 MCP（2024-11-05）/A2A 设计完备，但传输层是进程内 asyncio 字典路由，无网络实现
契约边界层间契约=Python 对象直传，无 IDL/序列化边界/跨层鉴权头 → 拆分服务前缺显式契约
数据迁移无 schema 迁移机制；schema_evolution.py 已实现未启用；画像 JSON 无 schema 版本
持久化仅 L2 画像落盘（非原子）；BKT/IRT/会话/知识库/审计全内存 → 重启丢失

九、建议的横向治理（按优先级）

优先级工作项解决
